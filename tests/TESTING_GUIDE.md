# Testing new vszip filters

This is the project standard for adding or substantially changing a filter.
The goal is not merely high line coverage: tests must let us optimize hot code
aggressively while detecting wrong pixels, unsafe inputs, SIMD tail bugs,
scheduling errors, and Debug/ReleaseFast differences.

## Definition of done

A new filter is test-ready when its tests cover:

- the public API contract: accepted formats, output format, dimensions, frame
  count, frame properties, optional arguments, defaults, and validation;
- an independent correctness oracle where one is practical;
- every plane the filter claims to process;
- integer and floating-point paths, including half precision if supported;
- normal, odd, tiny, cropped, and SIMD-boundary geometries;
- important algorithm branches and exact boundary values;
- multiple frames and non-sequential/concurrent requests when state or frame
  scheduling is involved;
- Debug and ReleaseFast builds;
- sanitizer, subprocess, or equivalent isolation for any call that could panic,
  abort, hang, or access invalid memory;
- a benchmark outside pytest when performance is part of the filter's purpose.

Goldens are useful regression locks, but a golden generated by the code under
test is not an independent proof of correctness. At least one invariant,
reference implementation, scalar model, or metamorphic property must say what
the output *should* be.

## 1. Derive the contract from code and experiments

Do not start by copying the wiki or an old test. Read these paths first:

1. the VapourSynth wrapper in `src/vapoursynth/<filter>.zig`;
2. the kernel in `src/filters/<filter>.zig`;
3. shared validation, format, plane, range, and scaling helpers;
4. plugin registration in `src/vszip.zig`;
5. any upstream implementation or formal algorithm reference;
6. existing tests for filters with the same data types or scheduling mode.

Write down, in the test module comments, the observable contract and the major
branches. Then confirm uncertain behavior with a small practical probe against
the built plugin. Documentation can be stale; an experiment can reveal current
behavior, but current behavior is not automatically the desired behavior. If a
probe exposes unsafe or nonsensical behavior, add a desired-contract test and
mark the known production failure explicitly.

Useful questions:

- Does an unprocessed plane come from the source, the filtered clip, or a newly
  allocated frame?
- Are thresholds expressed in 8-bit units, normalized units, or native sample
  units? Does range metadata affect scaling?
- Does the wrapper repeat the last array element across remaining planes?
- Does an empty or overlong array reach Zig, or does Python reject it first?
- Which formats reach a distinct compile-time specialization?
- Is the filter declared parallel, unordered, or serial?
- Can `NaN`, positive infinity, or negative infinity bypass comparisons?

## 2. Build a compact coverage matrix

Prefer a deliberate matrix over a Cartesian explosion. Each case should cover a
new branch or risk.

| Dimension | Minimum useful cases |
|---|---|
| Sample storage | u8, wider integer, f32; f16 if accepted |
| Color family | Gray plus every accepted YUV/RGB path |
| Planes | all planes, one selected plane, chroma-only where meaningful |
| Geometry | normal, odd, tiny, cropped/repacked |
| Width | `1`, `N-1`, `N`, `N+1`, `2N-1`, `2N`, `2N+1` for SIMD width `N` |
| Height | 1, odd, and enough rows to cross band/tile boundaries |
| Frames | first, middle, last; more than one frame for temporal filters |
| Values | min, max, neutral, threshold just below/equal/above |
| Arguments | omitted default, each branch value, valid extremes |
| Build | Debug and ReleaseFast; baseline CPU where supported |

Use `make_clip` for representative image data. Use `std.BlankClip`, tiny files,
or generated patterns for exact edge values. Random input is useful only with a
fixed seed and a clear oracle.

## 3. Choose the strongest available oracle

Use the highest item in this list that is practical.

### Independent scalar model

For a local per-pixel algorithm, implement a small readable Python formula. Do
not transliterate vector code instruction by instruction. State units and
rounding explicitly, generate values on both sides of every branch, and compare
every visible pixel.

```python
def reference_pixel(x, threshold):
    # Specification-level formula, not a port of SIMD intrinsics.
    return 0 if x < threshold else 255


@pytest.mark.parametrize("width", [1, 7, 8, 9, 15, 16, 17, 31, 32, 33])
def test_scalar_oracle(core, width):
    src = make_exact_input(core, width)
    out = src.vszip.NewFilter(threshold=10)
    assert visible_pixels(out) == [reference_pixel(x, 10) for x in input_pixels]
```

### Trusted external implementation

If an upstream implementation is available, test parity directly and explain:

- the exact upstream version or algorithm;
- any parameter or range mapping;
- whether the expected result is bit-exact or tolerant;
- why the selected tolerance is large enough but still sensitive.

Optional oracles should use `pytest.importorskip` or `skipif`. They supplement,
not replace, tests that always run.

### Metamorphic properties

When exact output is difficult to calculate, transform the input in a way that
implies a predictable output relationship. Examples:

- identity parameters produce bit-identical output;
- a stronger blur lowers a quality metric more than a weaker blur;
- processing only plane 0 leaves the other planes bit-identical to the defined
  passthrough clip;
- converting f16 output to f32 agrees with the native f32 path within the
  justified half-precision tolerance;
- requesting frames in another order produces the same per-frame result.

### Golden snapshots

Goldens are good for broad regression coverage after independent checks exist.
They are especially useful for filters with many branches or expensive
reference implementations.

```sh
pytest --update-goldens tests/test_new_filter.py
git diff -- tests/goldens/new_filter.json
```

Never update goldens merely to make a failure disappear. Explain why every
changed value is correct. Confirm sensitivity once by perturbing a stored value
and observing the intended test fail.

## 4. Compare the whole contract

`helpers.max_abs_diff()` compares one plane by design. Whole-image parity must
use `max_abs_diff_all_planes()` or `assert_same_clip()`.

```python
from helpers import assert_same_clip, max_abs_diff_all_planes

assert_same_clip(got, expected)                 # format, size, length, all pixels
assert max_abs_diff_all_planes(got, ref) <= 1  # tolerant, all planes
```

Also assert any contract `assert_same_clip` intentionally does not cover:

- required or removed frame properties;
- output color family and sample type when conversion is expected;
- whether output frames inherit properties from the correct input;
- finite values and legal range for floating-point output.

For tolerant comparisons, report the worst frame, plane, location if possible.
Avoid only checking mean error: opposite errors cancel, and a one-pixel memory or
tail bug can disappear in an average.

## 5. Target optimized-code risks

### SIMD boundaries and scalar tails

Test widths around the relevant lane count. A vector loop can be right while its
tail is wrong, or vice versa. Include two or more rows because stride and row
transitions are separate hazards. When lane count differs by CPU target, choose
widths that cover common 4-, 8-, and 16-lane boundaries.

### Crops, offsets, and stride

A crop can have a non-zero data offset and a parent stride larger than its
visible width. Compare processing a crop with processing a freshly repacked copy:

```python
from helpers import assert_same_clip, repack

cropped = src.std.Crop(left=2, right=6, top=2, bottom=4)
assert_same_clip(cropped.vszip.NewFilter(), repack(cropped).vszip.NewFilter())
```

### Plane routing

Use deliberately different values in each plane. A YUV/RGB test that compares
only plane 0 does not protect chroma, green, or blue kernels. Test per-plane
arrays with different arguments so accidental broadcasting is visible.

### Alignment and binary layout

If a measured optimization depends on `align(64)`, symbol presence, or another
binary property, encode that contract in a binary-level test such as
`test_alignment.py`. Such tests may skip on stripped binaries, but must run on
an unstripped CI build.

### Cross-build differential tests

Run the same deterministic cases against Debug, ReleaseFast, and relevant CPU
targets. Exact integer output should normally hash identically. Float output
must use a filter-specific tolerance justified by numerical analysis, not a
suite-wide guess.

Optimized builds are essential: undefined behavior, unchecked arithmetic, fast
floating-point transformations, and CPU-specific vector paths can be invisible
in Debug.

## 6. Validate hostile inputs safely

For every public parameter, test:

- just below minimum, minimum, maximum, and just above maximum;
- wrong enum values;
- too many array values and duplicate/out-of-range plane indices;
- mismatched width, height, family, subsampling, depth, and frame count;
- unsupported half/integer/float formats;
- `NaN`, `+inf`, and `-inf` for every floating-point argument.

`NaN` is special: both `nan < minimum` and `nan > maximum` are false. A range
check written only as two comparisons therefore accepts it. Validate finiteness
explicitly in production code.

If a case may crash, abort, hang, or corrupt the pytest process, isolate it:

```python
result = subprocess.run(
    [sys.executable, "-c", script],
    capture_output=True,
    text=True,
    timeout=30,
)
assert result.returncode == 0
assert "REJECTED" in result.stdout
```

The child should load the exact library selected by `VSZIP_LIB`. It should force
evaluation with `get_frame(0)`, because VapourSynth graph construction is lazy.
Prefer asserting a catchable `vs.Error`, not a particular signal or panic.

For a known defect, use `xfail(strict=True)` with a precise reason. Never use a
plain skip for a dangerous bug. Strict mode makes a fixed case XPASS-and-fail,
which forces cleanup of the marker.

## 7. Test VapourSynth scheduling semantics

A filter declared parallel must tolerate concurrent requests. A temporal filter
must calculate frame `n` from declared dependencies and frame numbers, not from
the order in which callers happened to request frames.

Test at least:

- sequential requests as the reference;
- a shuffled request order such as last, first, middle;
- concurrent requests through `ThreadPoolExecutor`;
- repeated requests for the same frame;
- boundary frames whose previous/next dependencies are missing.

Create separate output nodes for sequential and shuffled/concurrent runs so
VapourSynth's frame cache cannot make the test vacuous.

## 8. Keep performance tests honest

Correctness pytest and benchmarking serve different purposes. Do not put tight
wall-clock assertions in normal pytest: shared CI machines are noisy.

Maintain a repeatable benchmark for hot filters that records:

- exact revision and build mode;
- Zig version and target CPU;
- clip format, geometry, frame count, and arguments;
- warm-up policy and number of repetitions;
- median and dispersion, not only the best sample;
- one-thread latency and representative multithread throughput;
- output hashes or a correctness run from the same binary.

Use a broad performance guard only on controlled hardware. A useful workflow is
correctness first, output-hash equivalence second, benchmark last. Faster wrong
pixels are not an optimization.

## 9. Recommended module structure

"""Contract and oracle for NewFilter."""

Keep test names about behavior, not implementation details. Comments should
explain why the case exists and what regression it catches.

## 10. Local and CI workflow

Run focused tests while developing, then both complete build modes:

```sh
zig build -Doptimize=Debug -Dcpu=x86_64_v3
pytest -q tests/test_new_filter.py

zig build -Doptimize=Debug -Dcpu=x86_64_v3
pytest -q

zig build -Doptimize=ReleaseFast -Dcpu=x86_64_v3
pytest -q
```

When comparing more than one binary without rebuilding, set `VSZIP_LIB` to an
absolute library path. Do not load two versions of the plugin into one Python
process; run separate pytest or probe processes.

Before committing:

- inspect `pytest --collect-only -q` for unexpected missing tests;
- check skip and xfail reasons;
- make sure every golden file has a caller and every filter has a test module;
- review golden diffs rather than accepting them mechanically;
- run the new test once against a deliberately broken implementation or
  perturbed oracle/golden to prove it can fail;
- record benchmark results when hot code changed.
